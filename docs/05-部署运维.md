# 05 部署运维（NitroGateway）

> 版本：v1.0 ｜ 日期：2026-08-30 ｜ 依据：docker-compose.yml、Dockerfile、deploy/systemd/、.env.example、FACTORY-TEST.md

## 1. 部署形态总览

| 形态 | 平台 | 载体 | 适用场景 |
| --- | --- | --- | --- |
| 形态 1 · 现场边缘网关 · Linux | Linux | docker-compose.yml（mqtt + gateway + web） | 单点演示 / 出厂验证 / 现场运维；采集 + 本地库 + web 管理面板装在同一台机器 |
| 形态 2 · 现场边缘网关 · Windows | Windows | src/NitroGateway.Desktop（WPF） | 本机采集 + 本地库 + 本地 UI，MQTT 发布到配置的 broker |
| 中心（如需） | - | 独立项目（中心 webapi + Ingest） | web 已纯边缘化（ADR-054）；多现场中心另立项目，compose.center / ingest / center.db / sites 归档不删 |

边缘网关数据流：本机采集 → 本地 SQLite → MQTT 发布到 broker，谁订阅谁消费，不依赖中心（ADR-054）。

## 2. Docker compose 部署（形态 1 · Linux）

### 2.1 栈组成

| 服务 | 镜像 / 构建 | 端口 | 说明 |
| --- | --- | --- | --- |
| mqtt | eclipse-mosquitto:2 | 1883 | 现场上行汇聚，挂载 tools/mosquitto.conf |
| gateway | 根 Dockerfile（.NET 10） | 5100 | 采集 + 本地库 + 转发 + 告警 + API |
| web | web/Dockerfile（nginx） | 5170 → gateway:5100 | Vue 3 管理面板 |

### 2.2 启动 / 停止

```bash
# 首次（现场构建）：
docker compose up -d --build
# 查看：
docker compose ps
# 停止（保留数据卷）：
docker compose down
```

### 2.3 必需环境变量（未设置 compose 直接拒启）

| 变量 | 说明 | 生成建议 |
| --- | --- | --- |
| JWT_SECRET | JWT 签名密钥，≥32 字节强随机 | `openssl rand -base64 48` |
| ADMIN_PASSWORD | 内置 admin 密码（生产禁用 admin/admin123） | 强随机密码 |
| OPERATOR_PASSWORD | 内置 operator 密码（生产禁用 operator/oper123） | 强随机密码 |
| VIEWER_PASSWORD | 内置 viewer 密码（生产禁用 viewer/view123） | 强随机密码 |

`cp .env.example .env` 后填写；`.env` 已 gitignore，不入库。

- compose 用 `:?` 校验，任一变量缺失即拒绝启动。
- AddNitroSecurity 生产校验覆盖全部三个内置账号，**只覆盖 admin 也会启动崩溃**（2026-08-19 实测发现），三个都要设。

### 2.4 数据卷与日志

| 卷 | 挂载点 | 内容 |
| --- | --- | --- |
| gateway-data | /app/data | SQLite 数据库 nitrogateway.db（时序 + outbox + 告警 + 审计 + 用户等） |
| gateway-logs | /app/logs | Serilog 结构化 JSON 日志（日轮转，保留 7 天） |

- 备份建议：备份 gateway-data 卷即可（时序保留 30 天自动清理）；备份前先 `docker compose stop gateway` 保证 WAL 落盘。
- RTU 串口：Linux 主机按需把 `/dev/ttyUSB0`、`/dev/ttyS0` 透传进容器（compose 中 `devices:` 段，默认注释）。

### 2.5 端口占用提示

两个 compose 栈（边缘 / 中心）使用同一套宿主端口（1883/5100/5200/5170），正常运行二选一；需同时跑时用 `-p` 区分项目并覆盖端口：

```bash
docker compose -p center -f docker-compose.center.yml up -d
```

## 3. 本地开发启动

```bash
# 1. 启动 MQTT broker
docker compose up -d mqtt

# 2. 后端
cd src/NitroGateway.Webapi && dotnet run
#    API:   http://localhost:5100/swagger
#    指标:  http://localhost:5100/metrics
#    健康:  http://localhost:5100/healthz

# 3. 前端（另开终端）
cd web && npm install && npm run dev
#    前端: http://localhost:5173   登录: admin/admin123（仅开发默认账号）
```

> 注意：本机若常驻 Webapi 进程会锁 DLL，导致 `dotnet test` 增量构建 MSB3027 失败；测试前先停进程。

## 4. systemd 服务化 + 看门狗（边缘设备形态）

> 分支 `feat/edge-device-systemd`。目标：把「Docker compose 部署的服务器应用形态」往「Linux 边缘设备形态」靠——开机自启 + 崩溃自愈 + 健康看门狗。

三层自愈逻辑：

| 层 | 机制 | 负责什么 |
| --- | --- | --- |
| 容器级 | compose `restart: unless-stopped` | 单容器崩溃自动拉起 |
| 服务级 | `nitrogateway.service`（Type=oneshot, RemainAfterExit） | 断电重启 / 开机后整套栈自愈；关机优雅 `docker compose stop` |
| 健康级 | `nitrogateway-watchdog`（.service + .sh） | 进程活着但 /healthz 不健康时主动 `docker compose restart gateway` |

看门狗参数（/etc/default/nitrogateway，install.sh 生成）：`GATEWAY_URL=http://localhost:5100/healthz`、`CHECK_INTERVAL=10s`、`FAIL_THRESHOLD=3`（连续 3 次探测失败 → 重启 gateway）。

安装：

```bash
# 部署机上：需 curl、docker compose v2；STACK_DIR 为放置 docker-compose.yml 的目录
sudo bash install.sh /opt/nitrogateway
```

验证（故障注入，证明真能自愈）：

```bash
systemctl status nitrogateway-watchdog
docker compose -f /opt/nitrogateway/docker-compose.yml kill gateway   # 模拟崩溃/被杀
watch docker compose -f /opt/nitrogateway/docker-compose.yml ps       # ~30s 内拉回
journalctl -u nitrogateway-watchdog -f                                 # 看门狗日志
sudo reboot                                                           # 模拟断电重启 → 整栈自动恢复
```

卸载：`sudo systemctl disable --now nitrogateway nitrogateway-watchdog` + 删除 unit 文件 + `sudo systemctl daemon-reload`（详见 deploy/systemd/README.md）。

## 5. 发布与升级（GHCR 镜像）

镜像：`ghcr.io/jiujiugou/nitrogateway-gateway`、`ghcr.io/jiujiugou/nitrogateway-web`。
tag 策略：master → `latest` + `sha-<7>`；`vX.Y.Z` tag → `vX.Y.Z` + `sha-<7>`。

部署机从 GHCR 拉取发布产物（不再现场构建）：

```bash
docker compose -f docker-compose.yml -f docker-compose.cd.yml pull
docker compose -f docker-compose.yml -f docker-compose.cd.yml up -d
```

`docker-compose.cd.yml` 仅覆盖镜像来源（`image:` + `build: !reset` + `pull_policy: always`），mqtt/端口/卷/环境变量仍由 docker-compose.yml 定义；本地开发仍可直接 `docker compose up -d`（现场构建路径不变）。

> ⚠️ CI/CD 现状（如实）：`.github/workflows` 目录当前为空，流水线文件已随 commit `7098f80` 删除（ADR-058 已实施后删除）。以上 GHCR 流程描述的是曾建成的发布路径，本地/手动仍可套用（docker buildx + push + compose override）；自动化回归需恢复流水线，见 06 复盘。

## 6. 镜像构建注意（Dockerfile 陷阱）

- **Docker ARG 作用域**：FROM 前声明的全局 ARG（`APP_PROJECT`）在 build 阶段内不可见，必须在 build 阶段重新声明 `ARG APP_PROJECT`，否则 `dotnet restore` 回退还原 slnx、因容器内缺少 Desktop/Storage.Disk/tests 的 csproj 报 **MSB3202**（曾导致 center 镜像构建失败）。
- **监听地址**：运行镜像 EXPOSE 5100 + `ASPNETCORE_URLS=http://0.0.0.0:5100`，容器内必须监听 0.0.0.0，否则宿主机/前端容器无法访问 API（appsettings 默认 Urls=localhost 只在裸机开发时用）。
- **Storage.Disk** 被 Persistence/Collection/Forwarder/Webapi 硬引用，restore 阶段必须 COPY 其 csproj，否则发布 `--no-restore` 报 NETSDK1004。

## 7. 健康检查与排障

| 端点 | 含义 |
| --- | --- |
| /healthz | 存活（进程活着） |
| /readyz | 就绪（SQLite + MQTT + disk + http-ready tag） |
| /metrics | Prometheus 指标（16 个自定义 nitro_*） |

常见故障：

| 现象 | 排查 |
| --- | --- |
| 启动即退出 | 未设置环境变量（compose `:?` 拒启）；JWT 密钥太短；`docker compose logs gateway` 看报错 |
| 前端 502 | dev 模式 vite 代理 IPv6 已修（ADR-063：127.0.0.1）；生产 web 容器 nginx → gateway:5100，先确认 gateway 就绪 |
| 数据不上行 | 确认 MQTT:Host=mqtt（compose 内）、转发开关未关（/api/forwarder）、磁盘未 Critical、broker 通 |
| 积压上涨 | 转发固定上限限流（单次 ≤1000 批、单轮 ≤2000 批）；积压 >1000 批看 Warning 日志（首超立即、之后每 60s） |
| dotnet test MSB3027 | 本机 Webapi 进程锁 DLL，先停进程 |

## 8. 运维基线

- 时序保留 30 天自动清理；磁盘 <1GB 预警、<256MB 降级暂停转发，恢复余量 20% 回 Normal。
- 7×24 无人值守：每设备独立熔断器（故障隔离）、MQTT 自动重连（10 次 + backoff 1s→30s）、systemd + 看门狗自愈。
- 出厂门禁：T0~T7，P0+P1 全过才判定「可用、可长期运行」（FACTORY-TEST.md）。
