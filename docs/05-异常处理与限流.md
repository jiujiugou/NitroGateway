# NitroGateway 异常处理与限流机制

> 生成时间: 2026-08-08 | 用途: 现状梳理 + 讨论基线（代码为唯一事实来源，文档漂移以代码为准）

## 一、总体设计哲学

两条错误通道，按"是否热路径"分流：

| 通道 | 适用场景 | 机制 |
| --- | --- | --- |
| `OperationResult` | 采集/转发/存储等热路径 | 失败以返回值传递，**不抛异常**，避免热路径异常开销；错误带 `OperationalError`（Code/Category/Severity） |
| 异常 + catch | API 层、后台宿主循环 | 兜底捕获 → 记日志 → 转 500 JSON 或吞掉保证宿主存活 |
| `OperationCanceledException` | 全链路 | **不是失败**：取消单独 catch 并向上传播/正常退出，任何兜底 catch 不得吞掉 |

关键边界：协议层（`ReliableProtocolDriver`）把异常转成 `OperationResult`，因此采集热路径全程无异常传播；异常只出现在"宿主层"（引擎循环、Channel 消费、MQTT 重连）作为兜底。

## 二、错误模型（Shared）

- `OperationResult` / `OperationResult<T>`：`IsSuccess / IsFailure / Error`，`Error` 为 null 即成功（`src/NitroGateway.Shared/OperationResult.cs`）
- `OperationalError`：`Code + Message + Details + Severity + Category`，工厂方法 `Timeout / Communication / Protocol / General / Validation / Unavailable / Storage / StorageFull / DatabaseLocked` 等（`src/NitroGateway.Shared/OperationalError.cs`）
- 分类语义：`Communication`（链路抖动，可重试）、`Protocol`（协议解析/收发）、`Validation`（参数）、`Resource`（不可用）、`Storage`（落库）
- 严重性分级驱动日志级别：`Error` 级 → `LogError`，`Warning` 级 → `LogWarning`（例：`DataDispatcher.cs` 缓冲入队失败按 `Severity` 分流日志级别）

## 三、异常处理链路

### 3.1 协议层（失败不抛出）
- `ReliableProtocolDriver.ReadBatchAsync`：Polly 管线（重试 3 次 + 指数退避 500ms→1s→2s + 每次尝试独立 3s 超时）→ 最终失败转 `OperationResult.Failure(Protocol)` 返回，**不抛异常**；`OperationCanceledException` 单独 rethrow（`src/NitroGateway.Protocol/Abstraction/ReliableProtocolDriver.cs:92`）
- Modbus 批量读"全部点位均未取到" → 主动置 `Faulted`，让重试管线重新建连（`src/NitroGateway.Protocol/Modbus/ModbusDriverBase.cs`）
- 驱动接口统一返回 `OperationResult`，`IMqttClient` 同样约定（`src/NitroGateway.Transport/MQTT/IMqttClient.cs`）

### 3.2 采集层（宿主存活优先）
- `CollectionEngine`：`PeriodicTimer` 循环；单轮异常 → catch → `LogError` → 延迟 5s 重试，**引擎不退出**；`OperationCanceledException` → 正常关闭（`src/NitroGateway.Collection/CollectionEngine.cs:69`）
- `DeviceCollector`：轮级兜底 catch（`src/NitroGateway.Collection/Collector/DeviceCollector.cs:188`）；并发门控 `SemaphoreSlim(MaxConcurrency)` 保证并行上限
- 熔断器（按设备）：`HealthMonitor` 判定 Offline → `Trip()` 拒绝对离线设备的重复打击；冷却到期 → `HalfOpen` 放行 1 个探测；成功 `Closed`、失败翻倍冷却 5s→5min（`src/NitroGateway.Collection/Resilience/CircuitBreaker.cs`）

### 3.3 存储/事件层（Channel 隔离 + 跳过继续）
- `MeasurementWriteHost`：有界 Channel（1000 批，`DropOldest` 丢最旧）；单批写入异常 → `LogError` + **跳过该批继续消费**（`src/NitroGateway.Collection/Dispatcher/MeasurementWriteHost.cs:63`）
- `SinkDispatcher`：有界 Channel（1000 条）；单个 Sink 异常被内层 catch 隔离，**不影响其他 Sink**（`src/NitroGateway.Collection/Dispatcher/SinkDispatcher.cs:81`）
- `DataDispatcher`：双写三步骤互相独立——时序 Channel 满 → 丢弃+告警；缓冲入队失败 → 按严重性记日志；事件推送非阻塞（`src/NitroGateway.Collection/Dispatcher/DataDispatcher.cs:48`）
- `SqliteErrorClassifier`：`SqliteException.SqliteErrorCode` → 语义化错误：`13` 磁盘满 / `10` IO / `11` 损坏 / `5` 锁定（`src/NitroGateway.Persistence/Sqlite/SqliteErrorClassifier.cs`）

### 3.4 转发层（至少一次 + 重试超限丢弃，不静默丢数）
- `Forwarder.ForwardBatchAsync`：Dequeue 失败 → 返回 Failure + `LogError`（防"出队异常被吞、转发静默停滞"，ADR-001 P1-3①）；单批失败 → `MarkFailed`（重试计数+1 回 Pending，超限直接 DELETE 丢弃并上报 `dropped` 指标），**不阻塞后续批次**；仅发布成功才 `Commit`（至少一次语义）；`Commit/MarkFailed` 失败 → `LogError`（防批次卡 InFlight 静默丢数，P1-3②）（`src/NitroGateway.Forwarder/Forwarder.cs`）
- MQTT：`MqttClientWrapper` 指数退避快速重连；`MqttHostedService` 监督兜底重连（`Faulted` 必重连，`Disconnected` 仅当配置允许），Broker 恢复无需重启网关（`src/NitroGateway.Transport/MQTT/MqttHostedService.cs:47`）

### 3.5 API 层（兜底中间件）
- `ExceptionHandlingMiddleware`：未处理异常 → 500 JSON（`{ success=false, code="InternalError" }`）；**必须注册在 AuditMiddleware 内层**，保证审计记录真实状态码（`src/NitroGateway.Security/Audit/ExceptionHandlingMiddleware.cs:28`，ADR-004 P2-4）
- Controller 惯例：业务失败返回 `ApiResponse`（HTTP 200 + `success=false`），异常兜底走中间件 500

### 3.6 生命周期
- 优雅关闭 drain：采集→转发顺序停止，当前轮等待上限后强制取消（`CollectionEngine.StopAsync`）
- 全链路 `OperationCanceledException` 均按"正常关闭"处理，不做错误日志

## 五、背压与丢数据策略（与限流相关的取舍）

| 环节 | 满时行为 | 是否丢数 | 设计意图 |
| --- | --- | --- | --- |
| 时序写 Channel（1000 批） | `DropOldest` 丢最旧 + 日志 | 丢（最旧优先级最低） | 存储慢不阻塞采集热路径 |
| 事件 Channel（1000 条） | `DropOldest` 丢最旧 + 警告 | 丢（仅通知类事件） | Sink 慢不阻塞采集 |
| 转发缓冲 | 无限增长（SQLite Pending） | 不丢 | MQTT 断连期间本地累积，恢复后按固定批量上限(1000/轮)排水 |
| 转发失败批次 | 重试计数超限 → 直接丢弃 | 丢（坏消息，上报 dropped 指标） | 坏消息不阻塞后续批次 |

## 六、开放讨论点（待聊）

1. **API 层无全局限流**：未使用 ASP.NET Core `RateLimiter` 中间件，仅登录限流——边缘网关内网场景是否需要全局限流？
2. **`RateLimitValidator` 命名歧义**：它限的是"变化率"不是"请求频率"，与 `LoginRateLimiter` 的"限流"语义不同，名字易误导
3. **业务失败用 HTTP 200 包裹**（`ApiResponse.success=false`）：前端依赖 body 而非状态码，与 REST 惯例不同——是刻意的吗？
4. **时序 Channel 丢数与转发缓冲不丢数的不对称**：本地 SQLite 时序数据可能静默丢失（仅日志），无告警——是否该对齐转发层的"不静默丢数"原则？（注：2026-08-22 转发层已改为重试超限即丢弃，层级可靠性差异收敛）
5. ~~**`ForwardingThrottle` 全局共享**~~：2026-08-22 已删除 AIMD 节流，问题随设计一起消除
6. **熔断器状态不持久化**：重启后离线设备需重新积累失败次数才 Trip（前面已讨论，预热可缓解）
7. **`CollectionEngine` 单轮异常 5s 重试**：`PeriodicTimer` 不堆积轮次，但重试延迟期间整轮空转——对 1s 间隔是否有影响？
8. **登录限流内存实现**：重启清空、单实例——网关单实例内网场景合理，多实例部署时需要集中式限流
