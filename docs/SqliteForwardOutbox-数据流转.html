SqliteForwardOutbox 数据流转图

事务性 Outbox（forward_buffer 表）· 采集侧同步写入 → 转发侧异步消费 · 至少一次投递，消费端需幂等 · 悬停状态框可高亮相关流转

数据流转速览

  1. 入队：DataDispatcher 每采集周期把 BatchMeasurements 按通道（mqtt/http）各入队一行 → EnqueueAsync 序列化为 CamelCase JSON 后 INSERT，状态 Pending（retry_count=0）；Pending 超过上限（默认 10 万）拒绝入队。
  2. 出队：Forwarder（MQTT 5s 轮询）/ HttpForwarderEngine 调 DequeueAsync —— 同一事务内 SELECT + UPDATE 标记 InFlight（两阶段提交阶段一），事务外反序列化。
  3. 确认 / 失败：发布成功 → CommitAsync DELETE（仅删 InFlight，带状态守卫）；失败/异常 → MarkFailedAsync retry_count+1，< max 回 Pending 重试、≥ max 进 DeadLetter。
  4. 恢复与运维：崩溃遗留 InFlight 由 EnsureRecoveredAsync 启动时复位 Pending（可能重复投递）；死信可经 DeadLettersController 重试/丢弃，或由 DeadLetterRetentionService 按保留期周期清理；GetCountAsync 上报积压指标。

💡 悬停 Pending / InFlight / DeadLetter 三个状态框，会高亮与它相关的流转箭头。

Pending（待转发） InFlight（转发中） DeadLetter（死信） 成功路径（Commit 删除） 失败路径（重试/死信） 死信管理/人工重试 崩溃恢复 出队拉取

为什么是 Outbox 而不是内存 Buffer？ 它不是内存队列，而是一张持久化表 forward_buffer——采集侧同步写入、转发侧异步消费，进程崩溃不丢、重启续传，即"事务性 Outbox"模式。
至少一次（at-least-once）：出队标记 InFlight 与 Commit 删除之间若进程崩溃，遗留 InFlight 在下次启动首次使用时重置为 Pending 重新投递，因此可能重复投递，消费端须幂等。
两阶段提交：出队 = 事务内 SELECT + UPDATE 'InFlight'（阶段一），事务外反序列化；Commit 带状态守卫（仅删 InFlight 行），防止 stale commit 误删未发送数据。
