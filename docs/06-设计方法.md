# 设计方法（七问框架）

> 生成时间: 2026-08-10 | 用途: AI 时代个人设计方法论——代码交给 AI，设计留给人；适用于任何模块、契约、失败路径的"设计切片"

## 一、为什么需要这套方法

- AI 时代"写"的成本趋近于零（尤其应用层），价值转移到"设计"：决定做什么、边界在哪、数据怎么流、失败怎么办、怎么权衡
- 设计不是天赋，是一套可刻意练习的"提问 + 权衡"流程
- 进展慢的根源往往不是不会写，而是总想一次设计"整个项目"——正确做法是每次只设计一个切片，切片决策堆出整个系统

## 二、设计七问（每个切片过一遍，一屏内答完）

| # | 问题 | 要点 |
| --- | --- | --- |
| 1 | 目标 | 这一小块解决什么问题？验收标准是什么？ |
| 2 | 边界 | 哪些归我管？哪些明确不归我管？ |
| 3 | 数据流 | 数据从哪来、经过什么变换、到哪去？格式/频率/方向？ |
| 4 | 状态与失败 | 有哪些状态？每一步失败怎么办（超时/重试/幂等/降级）？ |
| 5 | 契约 | 接口/消息长什么样？谁来定版本？变更怎么演进？ |
| 6 | 规模与演进 | 现在多大？10 倍后哪里先崩？怎么演进不推倒重来？ |
| 7 | 权衡 | 为了简单放弃了什么？现在放弃是否合理？ |

## 三、演示：B 方案 MQTT 遥测契约（用七问走一遍）

场景：桌面采集端把点位遥测上报云端 Web 展示（多现场 → 一中心）。

- 目标：桌面采集端上报点位遥测，云端 Web 实时展示
- 边界：只管遥测上行；设备管理、配置下发不做
- 数据流：`Collection`(1s) → `Forwarder`(5s 批量) → broker → `Ingest`(订阅入库) → SQLite → Webapi → Vue
- 失败：断网 → 本地排队重传（已有死信/重试）；QoS1 重复投递 → 幂等去重；乱序 → 设备时间戳 + 序号
- 契约：topic `ng/{deviceId}/telemetry`，payload v1：`{ "msgId": "<全局唯一>", "ts": 1710000000, "points": [{"pointId":1,"value":12.3,"quality":0}] }`；`msgId` 即幂等键，落库建 `(deviceId, msgId)` 唯一索引
- 规模：单现场几千点、1s 频率 ≈ 每秒几百条，MQTT+SQLite 无压力；×10 后上批量压缩、分主题，字段带版本号兼容演进
- 权衡：JSON 好调试、牺牲带宽；不做 QoS2（至少一次足够），换吞吐

15 分钟输出以上内容，就是"设计"。不是灵感，是把七问回答完。

## 四、训练方法（三个动作）

1. **设计先行**：任何功能先写一屏"七问答案"，再让 AI 写代码；项目 `notes/ADR/` 就是设计决策的落点
2. **逆向工程**：读现有代码问"为什么这么设计"（例：采集与转发为什么分离、为什么双写、为什么熔断），答案写进 ADR
3. **只设计切片，不设计系统**：一次只设计一个契约/模块/失败路径，每个 15 分钟；整个系统是切片决策的集合

## 五、与仓库规则的关系

- `notes/ADR/` = 设计决策记录（为什么这么设计）
- `notes/worklog/` = 结论与当前目标
- `docs/` 编号文档 = 知识沉淀（本文件属于此类）
