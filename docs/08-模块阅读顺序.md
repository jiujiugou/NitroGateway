# 08 模块阅读顺序（理解这套系统的主线）

> 目的：把 NitroGateway 从"AI 写的 37k 行"变成"我能脱稿讲清的骨架"。
> 原则：**不按依赖图从底向上读**（那会从空接口开始、枯燥且无主线），而是**跟着"一个数据点的一生"走**。

---

## 为什么是这个顺序

1. 数据流就是系统的真实运行方式——顺着它读，读到哪一步都清楚"这段在整条链路里干什么"。
2. 面试官也是顺着数据流问的："数据从 PLC 进来之后到哪去了？"
3. 依赖图适合"改代码"时查，不适合"建心智模型"。

---

## 第一遍：主线——一个数据点的一生（重点，必须深挖）

| 顺序 | 模块 | 看什么 | 深度 |
|---|---|---|---|
| 0 | `Domain` + `Shared` | 词汇表：`OperationResult`、`PointSnapshot`、`DevicePoint`、`MeasurementRecord`、`QualityCode` | ✅ 已看 |
| 1 | `Protocol.Abstractions` | `IProtocolDriver`、`RawPointValue`——**数据从哪进来**；为什么 Modbus/S7/OPC UA 能共用一套抽象 | 深 |
| 2 | `Protocol.Modbus` | `ModbusDriver`、`ModbusAddressParser`——第一个真实驱动 | 深 |
| 3 | `Collection` | `CollectionEngine` → `DeviceReader` → `PointValuePipeline` → `ChangeDetector` → `DataDispatcher`——**数据怎么流动、清洗、过滤** | 最深 |
| 4 | `Collection/Resilience` + `Device/DeviceHealthMonitor` | 熔断 + 健康判定——**设备坏了怎么办** | 最深 |
| 5 | `Storage.*`（接口层） | `IForwardBuffer`、`IMeasurementStore` 等——**出口的契约** | 中 |
| 6 | `Forwarder` + `Transport.MQTT` | outbox 排水 + 发布——**数据怎么可靠上云** | 最深 |
| 7 | `Persistence/Sqlite` | 上面那些接口的真实实现——**数据到底存哪了** | 中 |
| 8 | `Webapi` + `web` | REST、SignalR、DI 组合根——**数据怎么被人看到** | 中 |
| 9 | `Command` + `Device/Writing` | 命令回写闭环（云→网关→PLC，幂等+回执）——**数据怎么反向控制设备** | 深 |

> **第 3、4、6 站是核心**：要能各讲 20 分钟。其余能讲清"职责 + 接线"即可。

---

## 每一站的自检标准（读完必须能答，答不出就停）

1. 这个模块**接收什么、产出什么**？
2. 它**依赖谁**？为什么依赖方向是这个方向？
3. 它内部有**哪个承重设计**？——**替代方案是什么、为什么不用、代价是什么**？
4. 如果它**挂了**，系统会怎样？（故障模式）

> 第 3 条是全套方法的核心。能说出"替代方案 + 代价"，这个设计才算从 AI 的变成你的。

---

## 承重梁清单（面试必问，优先掌握）

1. **Outbox 至少一次 + 死信**：Pending → InFlight → Commit，崩溃不丢数；代价 = 会重复，靠消费端幂等兜。
2. **健康判定与熔断分离**：HealthMonitor 是唯一健康权威，CircuitBreaker 只做执行门控；代价 = 隔离有 3 次失败延迟。
3. **死区抑制 + 心跳兜底**：省流量但不"假存活"；只做死区会让云端把"链路断了"误读成"值没变"。
4. **命令回写闭环**：幂等（commandId）+ 回执（ack）；写值经 WriteGuard 三级门控。
5. **web 纯边缘化（ADR-054）**：边缘自治，不依赖中心；代价 = 无全局视图（由独立的 NitroCloud 补）。

## 已攻克的决策（用"需求 / 方案 / 代价"三件套记录）

### 决策 1：用 `OperationResult` 表示运行错误，而不是抛异常

- **需求**：单个设备/点位超时、连不上，不能影响其他设备，更不能拖垮全局。
- **方案**：设备 I/O 边界返回 `OperationResult`；程序性错误（参数非法、地址越界）仍抛异常。
- **为什么不用异常**：
  1. 超时/CRC 失败是**高频预期事件**，异常要栈展开，热路径代价高；
  2. 语义上这不是"异常"，是"设备在说话"，异常应留给"程序写错了"；
  3. `OperationalError` 带 `Category`/`Severity`，调用方可据此决定**重试 / 熔断 / 告警**。
- **关键区分**："防全局崩溃"是**需求**，`try/catch` 也能满足；选 Result 的理由是**成本、语义、结构化**。
- **代价（原罪）**：忘记检查返回值 → 错误**静默消失**，不报错、不崩溃、只是数据悄悄没了。
  - 推论：每个返回 `OperationResult` 的调用点都必须被检查或记录，否则这套设计会**静默背叛**你。
