# 02 架构设计（NitroGateway）

> 版本：v1.0 ｜ 日期：2026-08-30 ｜ 依据：代码现状 + notes/ADR（035/054/001/053/016 等）

## 1. 架构总览

NitroGateway 采用**分层 + 模块化**架构，21 个项目（slnx 收录），单向依赖，无循环引用。边缘网关是「一台机器上跑整套引擎」的自治节点：采集 → 本地库 → 转发，谁订阅谁消费，不依赖中心。

```
┌─────────────────────────────────────────────────────┐
│                    领域层                            │
│  Domain/         设备、点位、快照、协议抽象          │
│  Shared/         OperationResult (Category+Severity)│
├─────────────────────────────────────────────────────┤
│                    应用层                            │
│  Collection/     采集引擎 + 熔断器 + 通道分发        │
│  Forwarder/      MQTT/HTTP 转发 + 固定批量上限       │
│  Command/        命令订阅 + 幂等 + 回执（ADR-069）   │
│  Device/         设备/点位管理 + 健康监控 + 批量服务  │
│  Alarm/          告警规则评估 + Duration 去抖        │
├─────────────────────────────────────────────────────┤
│                  基础设施层                          │
│  Persistence/    SQLite 实现 (EF Core + Dapper)      │
│    └ Sqlite/     DbContext、存储、缓冲(outbox)、告警 │
│  Protocol/       Modbus TCP/RTU、S7、OPC UA 驱动     │
│  Transport/      MQTT (TLS+重连)、HTTP               │
│  Telemetry/      Prometheus + Activity Tracing       │
│  Storage/        纯接口层 (IMeasurementStore 等)     │
│  Security/       JWT + RBAC + WriteGuard + 审计      │
├─────────────────────────────────────────────────────┤
│                    编排层                            │
│  Host/           GatewayLifecycle (关闭时的 drain)   │
├─────────────────────────────────────────────────────┤
│                    表现层                            │
│  Webapi/         REST API + SignalR + HealthChecks   │
│  web/ (Vue 3)    设备管理 + 实时监控 + CSV 导入导出   │
│  Desktop/ (WPF)  Windows 边缘端壳（复用引擎类库）    │
└─────────────────────────────────────────────────────┘
```

### 分层职责与依赖纪律

- `Domain/`、`Shared/`：不引用任何基础设施，纯 C# 领域模型。
- `Storage/`、`Protocol/Abstraction/`：纯接口层，接口只增不删，隔离实现（Sqlite / 各协议驱动）。
- 基础设施（Persistence/Protocol/Transport/Telemetry/Security）实现接口，向上为应用层服务。
- Webapi/Desktop 作为组装根，把所有模块接线；Host 管理生命周期。

## 2. 部署形态（ADR-054/035）

两种自包含边缘壳，同一套引擎，互不依赖：

| 形态 | 平台 | 载体 | 说明 |
| --- | --- | --- | --- |
| 形态 1 · 现场边缘网关 · Linux | Linux | docker-compose.yml | 采集 + 本地库 + web 管理面板装同一台机器（边缘盒子/工控机），适合单点演示/出厂验证/现场运维 |
| 形态 2 · 现场边缘网关 · Windows | Windows | src/NitroGateway.Desktop（WPF） | 本机采集 + 本地库 + 本地 UI，MQTT 发布到配置的 broker（默认 localhost，可用 MQTT__Host/Port 覆盖） |
| 中心（如需，待独立项目） | - | 独立项目（中心 webapi + Ingest） | web 已不再承担中心库角色；docker-compose.center.yml、ingest、center.db、sites 表暂归档不删（ADR-054） |

### 边缘网关数据流

```
本机采集 → 本地 SQLite → MQTT 发布到 broker → 谁订阅谁消费（不依赖中心/Ingest）
```

### 部署栈（形态 1）

```
docker-compose.yml
├── mqtt      eclipse-mosquitto:2        :1883
├── gateway   后端（Dockerfile 构建）     :5100
└── web       Vue 构建产物（nginx）       :5170 → gateway:5100
```

## 4. 核心数据流

```
Modbus TCP PLC (:502)
      │
      ▼
DeviceReader ─── 3 次重试, 指数退避
      │
      ▼
PointValuePipeline ─── 类型转换, 工程缩放, 死区过滤, 点位级降频
      │
      ▼
DataDispatcher ─── 双写: SQLite MeasurementStore + ForwardOutbox
      │
      ├── SQLite (本地时序)
      └── ForwardOutbox ─── Pending → InFlight → Commit（两阶段）

ForwarderEngine (5s 周期, 首轮立即执行)
      │
      ▼
Forwarder ─── Dequeue(≤1000) → Serialize(JSON) → MQTT Publish(QoS1) → Commit
      │
      └── 失败 → MarkFailed → retry+1 → ≥5 → DeadLetter

命令回写（云 → 网关 → PLC）
      │
      ▼
CommandHostedService 订阅 nitrogateway/+/+/commands (QoS1)
      │
      ▼
CommandProcessor ─── 幂等(commandId) → IWriteService 写值 → 回执发布 commands/ack
```

## 7. 容错与可靠性设计

### 7.1 熔断器（CircuitBreaker）

- 每设备独立熔断器，线程安全（lock）。
- Closed → 连续 5 次失败 → Open（拒绝采集）→ 冷却 30s → HalfOpen → 探测成功 → Closed；探测失败 → Open（冷却 ×2，上限 5min）。
- HalfOpen 并发保护：同时只允许一个探测请求；探测超时 30s 自动释放锁。

### 7.2 转发可靠性（两阶段提交）

- `forward_outbox` 表：Pending → InFlight → Commit(删除) 或 MarkFailed(retry+1)。
- retry_count ≥ 5 → DeadLetter，不再被 Dequeue 取出。
- 单批失败不阻塞后续批次；Commit/MarkFailed 失败记录 Error 级日志防静默丢数。
- 停机 drain：采集侧停止后，MQTT 仍连接时把剩余批次尽量发完。

### 7.3 转发限流（2026-08-22 起简化）

- 以**固定批量上限**替代 AIMD 自适应节流：单次出队 ≤1000 批、单轮排水 ≤2000 批，防 MQTT 恢复瞬间冲垮 Broker。
- 积压告警：>1000 批记录 Warning（首超立即、之后每 60s 一次，回落后重置）。
- 磁盘 Critical 时跳过本轮出队，剩余批次留缓冲等恢复续传。

### 7.4 数据量抑制（ADR-053）

- 死区变化抑制：值变化超过死区才放行；未变化时按心跳兜底（300s）周期上报。
- 存储 / MQTT / SignalR 共用同一放行子集，避免三路数据量放大。

## 9. 安全架构

```
认证  JWT Bearer（POST /api/auth/login），登录限流
授权  RBAC：Admin / Operator / Viewer，5 个策略
写值  WriteGuard：设备模式 + 值范围 + 变化率三级门控（FluentValidation）
审计  AuditMiddleware：所有 /api/* 访问记录结构化日志
SignalR  连接时 query string 传 JWT token（禁止匿名订阅）
用户  DB 化 users 表 + 管理接口（ADR-066），首启从配置种子灌入
```

生产强制：`JWT_SECRET` / `ADMIN_PASSWORD` / `OPERATOR_PASSWORD` / `VIEWER_PASSWORD` 未设置直接拒启（compose `:?` 校验 + AddNitroSecurity 校验），禁用仓库内测试账号与开发密钥。

## 10. 配置热加载

```
Web API → DeviceManager → DB 保存 → StatusChanged 事件
    → 采集线程读 DeviceCache（内存）
    → 当前周期不中断, 下一周期自动切换
```

## 11. 非功能架构决策

| 维度 | 决策 |

| 单机自治 | 不依赖中心；断网本地照常采集存储，恢复后续传 |
