## 架构讨论：web 定位（2026-08-18）

### 结论（用户拍板）

- web 保持**单一身份**，不做复合（不兼做"边缘网关 + 中心库"）→ 收敛为纯边缘（Linux 网关管理端）。
- 桌面端 = Windows 边缘（自包含组合根，`GatewayHost` 全模块进程内）；web = Linux 边缘（webapi Gateway 形态 + Vue）。
- 双方完全独立各自运行、各自功能完整，**不需要同时启动**——同一台机器同时起会双写同一 SQLite + 双 MQTT 发布。
- 中心（Ingest / center.db / sites / Center 模式）**待定**：先归档不删；若要中心则独立建项目，不复用 webapi 双模式。

### 现状核对（代码事实）

- 桌面端 `GatewayHost.cs`：无 Kestrel、无 Webapi 引用，唯一外部依赖是可选 HttpClient（中心配置导入）→ 已自包含。
- webapi 当前双身份：`Deployment:Mode=Gateway|Center`（Program.cs `if (!isCenter)` 裁剪注册 + 前端 mode 机制）。
- Ingest：独立进程，订阅 `nitrogateway/+/+/measurements|alarms` → center.db（中心库唯一写点）。

### web 相比桌面的缺口（见 ADR-055）

- 实时监控无曲线（桌面 LiveCharts2，web 只有数值卡片）。
- 点位 CSV 导入未接线（后端 `PointImportController` 有，前端没接）。

### 待定 / 下一步

- 是否需要多现场中心？（决定 Ingest/center 是"删"还是"独立建项目"）。
- 代码改动清单（拆复合 + 补缺口）待用户确认后实施；实施后跑构建 + 全量测试。

## 桌面端 MQTT 定位澄清（用户拍板，2026-08-18）

- 桌面端 MQTT **独立旁路**：只按配置的 broker 发布（默认 localhost:1883），**不面向中心/Ingest**；
  任意 MQTT 订阅端订阅 `nitrogateway/{siteId}/{deviceId}/measurements|alarms`（QoS 1）即可消费。
- 桌面端自身不订阅不消费，本地展示走 SQLite + EventBridge；本地 SQLite 是桌面端自身可靠存储。
- 遥测走 MQTT、配置同步走 HTTP 中心 Webapi，两条通道独立。
- 已写入 `docs/11-桌面端WPF功能清单与架构.md` 新增「MQTT 数据上行（独立发布，不依赖中心）」小节。
