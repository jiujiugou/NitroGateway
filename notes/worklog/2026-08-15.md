## 实施: 桌面切换卡顿——SQLite 查询移出 UI 线程（ADR-047，2026-08-15）
- 背景: 用户反馈「切换窗口/设备点位卡顿」，LiveCharts2 性能已由 ADR-045 处理过；ADR-047 定位第二个根因——
  `RealtimeViewModel`/`HistoryViewModel` 从 UI 线程事件回调发起 SQLite 查询，Microsoft.Data.Sqlite 的
  `OpenAsync`/Dapper `QueryAsync` 是「同步外包」（在调用线程同步跑完才返回已完成 Task，await 不让出线程池），
  切设备/切回实时页/查历史时冻结窗口。
- 三问: 为什么做=UI 线程被 SQLite 查询同步阻塞导致窗口/设备点位切换卡顿；验收=查询全部移出 UI 线程、
  build+全量测试全绿；不做=切卡持续（7×24 表增长后更明显）。
- G1 确认: 行为变更（store 查询异步化，UI 不再因查询冻结）；采集/存储/转发逻辑不动。
- 探测（临时项目，废弃不提交）: 120 万行 ROW_NUMBER 分区查询在调用线程同步跑完（阻塞约 3.8s）；
  `Asynchronous=True` 在 Microsoft.Data.Sqlite 10.x 已移除，连接串方案不可行 → 只能 VM 侧 `Task.Run`。
- 代码改动（`src/NitroGateway.Desktop`，未升级/降级依赖包）:
  - `ViewModels/RealtimeViewModel.cs`: `LoadPointsAsync` 的 `_store.QueryLatestAsync`、
    `LoadPointHistoryAsync` 的 `_store.QueryPagedAsync` 均包 `Task.Run`；历史查询先捕获 `deviceId` 局部变量。
  - `ViewModels/HistoryViewModel.cs`: `QueryPageAsync` 先捕获 `deviceId`/`pointId` 局部变量，
    `_store.QueryPagedAsync` 包 `Task.Run`。
  - `_cache.GetAllAsync()` 保持原样（内存热路径 + EF Core 真异步，非 SQLite 同步外包）。
- 测试（`tests/NitroGateway.UnitTests`）: `StagedMeasurementStore` 加锁 + `PagedDequeueCount` 出队计数；
  两个竞态测试在触发第二次查询/断言前 `TestWait.UntilAsync(() => store.PagedDequeueCount >= 1)`
  （Task.Run 后出队在线程池，FIFO 顺序不确定，需等待查询真正触达存储）。
